# 방문·상담 측정 연결 상태

2026-11-12 운영 연결 확인. Firebase 프로젝트 `okclean-admin`의 기본 Firestore에 `site_events` 규칙을 적용한 뒤, 기존 Google 관리자 계정으로 시험 이벤트 저장 및 서버 재조회를 확인했다. 이 배포는 `analytics-config.js`의 `enabled`와 `verified`를 모두 true로 설정하여 새 방문·버튼 이벤트 수집을 활성화한다. 이전 방문 기록을 소급해서 만들지 않는다.

## 파일과 연결

- `analytics-config.js`: 공통 수집 설정. `enabled: true`, `verified: true`. 둘 중 하나라도 false이면 새 방문·상담 이벤트 전송은 중지된다.
- `analytics.js`: 허용된 이벤트/유입 출처/페이지 종류/서비스 종류/버튼 위치/상담 종류만 만드는 수집 모듈. 실제 운영 전송은 두 설정이 모두 true일 때만 가능하다.
- `admin/analytics.html`: 기존 Google 관리자 UID로 조회하며, 실패·권한 미확인은 숫자 0으로 대신하지 않는다. 실제 문의·예약 수는 표시하지 않는다.
- `ops/firestore.rules.current.txt`: 2026-11-12 실제 적용한 전체 규칙. 현재는 90일 정리 조건을 포함한 `firestore.rules.retention-20261112.txt`와 동일하다. 초기 수집 규칙의 보관본은 `firestore.rules.analytics-20261112.txt`이다.
- `analytics-maintenance.js`: 기존 Google 관리자 인증을 확인한 뒤 `site_events`의 90일 초과 자료만 조회·정리한다. 관리자 화면 접속 시 1회 실행하며 자동 예약 작업은 아니다. 세부 적용 상태는 [보관기간 문서](analytics-retention.md)를 따른다.
- `ops/firestore-site-events.proposed.txt`: 적용한 블록의 참고용 발췌. 파일 이름은 기존 검토 문서 링크를 유지하기 위해 보존했다.
- `ops/firestore-validation-20261112.json`: 격리된 Emulator 검증 63건과 실제 서버 시험 저장·조회 확인 근거.

홈페이지와 측정 대상 페이지에서 아래 스크립트를 차례대로 로드한다. 하위 서비스 페이지는 상대 경로를 `../`로 조정했다. 같은 페이지에 중복 삽입하지 않는다.

```html
<script src="analytics-config.js"></script>
<script src="analytics.js"></script>
```

신규 회원 저장이 서버에서 확인된 성공 분기에만 아래 호출이 연결되어 있다. 기존 접수증 재사용, 단순 가입 버튼 클릭, 실패 분기에서는 호출하지 않는다.

```js
window.OKCleanAnalytics?.track('signup_complete', { placement: 'other', target: 'none' });
```

일반 버튼은 DOM 위임으로 측정한다. 새 직접 상담 버튼이 팝업을 열면 `data-contact-kind="direct"`를 붙인다. 견적 팝업의 원래 `qKakao`는 자동으로 `quote`로 분류한다. 명시적 위치는 `data-analytics-placement="hero"`처럼 허용된 값으로 줄 수 있다. 채용·협업 영역 `.recruit`, `data-analytics-ignore` 아래 요소, 가입정보 전송 `jKakao`는 청소상담 집계에서 제외한다.

기존 `data-placement`/`data-cta-location`도 지원한다. `hero`는 `hero`, `quote-guide`/`quote-sheet`는 `quote`, `dock`은 `sticky`, `featured`/`cases`/`premium`/`service-top`/`service-bottom`/`area-top`/`area-bottom`은 `service`로 묶는다. 속성의 원문이나 알 수 없는 값은 서버에 전송하지 않는다.

## 개인정보와 수집 범위

방문·상담 `site_events`의 전송 필드는 `schema`, `event`, `source`, `page`, `service`, `placement`, `target`, `test`, 서버 시각 `at`뿐이다. 모든 텍스트 값은 코드와 규칙에 있는 열거값이다. 이름·전화번호·주소·지역 선택·희망 날짜·금액·견적 본문·회원 UID·쿠폰번호·전체 URL·쿼리·리퍼러 주소·사용자/광고 식별자를 전송하지 않는다. URL 쿼리 중 `src`/`utm_source`는 허용된 출처 명칭으로만 변환하며, 알 수 없는 값은 `other`로 버린다. 리퍼러는 호스트를 출처로 분류한 뒤 원문을 저장하지 않는다.

추천제품 판매처 버튼의 기존 `product_clicks` 수집은 별도 경로로 유지한다. 해당 문서에는 제품 식별자 `product`, 허용된 유입 분류 `src`, 서버 저장 시각 `at`만 보낸다. `src`는 원본 쿼리 값을 직접 저장하지 않고 `OKCleanAnalytics.status().source`를 사용한다. 방문·상담 통계의 연결 대기 설정과 기존 제품 클릭 수집의 운영 상태는 구분한다.

개인정보처리방침의 동일한 수집 끄기 선택은 `site_events`와 `product_clicks` 양쪽의 새 기록에 적용된다. 제품 클릭 쓰기는 `optedOut` 또는 점검 모드 `debug`이면 생략한다. 기존 제품 클릭 스키마에는 시험 플래그를 추가하지 않으므로 시험 클릭은 별도 기록하지 않는다. 사용처가 없던 `okclean_product_clicks` 로컬 추가 기록 코드는 제거했으며, 이용자 브라우저에 이미 저장된 과거 자료를 삭제하지는 않는다. 제품 구매 링크·공유·제품별 연결 주소의 동작은 유지한다.

30분 동안 같은 탭의 출처를 이어가기 위해 출처 열거값과 만료 시각만 sessionStorage에 저장한다. 서버 수집과 점검 모드가 모두 꺼져 있으면 이 저장도 하지 않는다. 별도의 사용자/세션 식별자를 만들지 않으므로 순방문자·중복 제거 고객 수는 계산할 수 없다.

개인정보처리방침의 수집 끄기/켜기는 localStorage의 `okclean_analytics_choice_v1` 한 키에 `off`/`on`만 저장한다. 끄기 선택 또는 선택 저장소 읽기 실패 시 초기 출처 저장·페이지 조회·일반 이벤트·관리자 시험 쓰기를 중지한다. SDK/인증 준비가 끝난 쓰기 직전에도 선택과 변경 번호를 다시 확인하여, 준비 도중 끄거나 껐다 켠 이전 이벤트가 뒤늦게 전송되지 않게 한다. 이미 시작된 네트워크 쓰기의 취소·기존 서버 기록 삭제는 수행하지 않는다.

끄기는 예약된 견적 점검 타이머와 analytics 전용 source/debug/log 세션 키만 정리하며 기존 회원·견적 저장은 건드리지 않는다. 같은 브라우저의 다른 탭에서도 `storage` 변경을 확인한다. 켜기는 운영 `enabled`/`verified`를 변경하지 않으며, 이후 새로 발생한 행동에 적용한다. 과거 행동을 모아 두거나 재전송하지 않는다. 선택 저장 자체가 실패하면 해당 페이지에서 수집을 멈추고 저장 실패를 표시한다.

`privacy.html` 1~6항은 유지하고 이 기능의 항목·목적·저장 수단·직접 식별자 미저장·출처 재사용 기한·`site_events` 90일 보관 기준과 관리자 접속 시 정리 방식, `product_clicks` 자동 삭제 미설정 사실을 추가했다. 이번 활성화 배포는 두 설정을 true로 변경하며, 서버 수집을 중단하려면 두 값을 false로 돌려서 배포한다. 이미 저장된 자료나 기존 회원 기능은 이 설정으로 변경되지 않는다.

`?analytics_test=1`은 이 탭의 점검 모드를 켜며, 전송 시에는 `test: true`만 붙인다. 점검 모드는 관리자 화면에서 끌 수 있다. 운영 설정이 꺼져 있으면 점검 기록은 현재 탭에만 최대 80건 남고 외부 전송은 없다. 시험 저장은 규칙상 기존 관리자에게만 허용한다.

## 추천제품 내부 이동 도착의 기록 기준

`shop_open`은 추천제품 링크를 누른 문서가 아니라 도착한 `/shop/` 또는 `/shop/index.html` 문서에서 한 번 기록한다. 링크 클릭 후 같은 탭이 이동하면서 기존 문서의 비동기 전송이 끝나지 못하는 경우를 줄이기 위한 변경이다. 고객의 페이지 이동을 늦추지 않으며, 재시도 큐나 새 식별자를 만들지 않는다.

도착 페이지의 `PerformanceNavigationTiming.type`이 `navigate`이고, `document.referrer`가 같은 사이트의 `/shop` 및 그 하위 경로 이외 페이지일 때만 기록한다. 외부·직접 진입, 새로고침(`reload`), 뒤로/앞으로 이동(`back_forward`), shop 자체 이동에는 추가하지 않는다. navigation 항목이나 리퍼러를 확인할 수 없으면 추정하지 않고 생략하므로 일부 내부 이동은 집계되지 않을 수 있다. 클릭 시점에는 `shop_open`을 전송하지 않아 클릭과 도착의 이중 집계를 방지한다.

유입 출처는 기존 30분 재사용 기준을 따르고, 수집 거부와 시험 표식도 그대로 적용한다. 도착 이벤트는 `page: shop`, `service: unknown`, `placement: other`, `target: none`으로 기록하며 출발 페이지의 전체 주소나 버튼 위치를 새로 저장하지 않는다. `page_view`는 추천제품 페이지 조회로 별도 유지한다. 관리자 화면의 추천제품 이동 수치는 상품 구매나 판매처 버튼 클릭 수가 아니다. 기존 클릭 기준 기록이 있다면 이번 변경 이후의 도착 기준 기록과 의미가 다를 수 있다.
